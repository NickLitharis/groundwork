# Sources and Scope

This skill is an original synthesis of measurement-led engineering guidance, not a verbatim combination of other skills. The references below identify material actually inspected while authoring. They support the specific practices noted; examples and recommendations labeled as application are this skill's synthesis, not claims that a source proved universal results.

## Inspected sources

- Eric S. Raymond, *The Art of Unix Programming* (2003), [Chapter 12: Optimization](https://cdn.nakamotoinstitute.org/docs/taoup.pdf), printed pp. 329–336 (PDF page labels). Inspected “Measure before Optimizing” (profiler intuition limits, instrumentation and external-latency noise, repeated workloads and correctness regression testing, varying parameters/modeling); “Nonlocality Considered Harmful” (memory hierarchy and optimizations that can become pessimizations); “Throughput vs. Latency,” “Batching Operations,” “Overlapping Operations,” and “Caching Operation Results” (latency, throughput, batching, overlap, and cache-coherence costs). **Book-derived principles:** measure the real bottleneck; understand how cost changes with workload; weigh latency, throughput, locality, and complexity. **Limits:** a 2003 text; hardware ratios, tool examples, and advice to favor latency are historical/context-dependent, not current measurements or universal priorities. It does not address present-day managed runtimes, JITs, containers, or modern deployment quotas. **Modern application:** choose objectives from the actual workload; treat batching, caching, and parallelism as measured tradeoffs; validate on the current runtime, hardware, and resource limits. These adaptations are this skill’s synthesis, not claims that the book studied those systems.
- Google, *Site Reliability Engineering* (Niall Richard Murphy, Betsy Beyer, Chris Jones, and Jennifer Petoff; O’Reilly Media, April 2016; [publisher listing](https://www.oreilly.com/library/view/site-reliability-engineering/9781491929117/)), [Chapter 4: Service Level Objectives](https://sre.google/sre-book/service-level-objectives/), sections “Indicators in Practice,” “Collecting Indicators,” and “Aggregation.” Inspected discussion distinguishes user-relevant measures from convenient proxies, request latency/throughput/correctness, and distributions/tails from averages; warns that aggregation windows can hide bursts and that mixed workload classes may need distinct objectives. **Book-derived principle:** define the measured behavior and population before comparing results; averages can conceal important tail behavior. **Limits:** written for service objectives and operational monitoring, not a universal mandate to define SLOs for local code changes or report a fixed percentile. **Modern application:** match metric, window, and workload to the decision, and use relevant tail quantiles for latency-sensitive work.
- Google, *Site Reliability Engineering* (Niall Richard Murphy, Betsy Beyer, Chris Jones, and Jennifer Petoff; O’Reilly Media, April 2016; [publisher listing](https://www.oreilly.com/library/view/site-reliability-engineering/9781491929117/)), [Chapter 6: Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/), sections “The Four Golden Signals,” “Worrying About Your Tail,” and “Choosing an Appropriate Resolution for Measurements.” Inspected latency, traffic, errors, and saturation; histogram-based latency distribution; tradeoffs in observation granularity and collection costs. **Limit:** operational monitoring recommendations are not a benchmark recipe. **Application:** inspect latency tails and the constrained resource when relevant, but keep instrumentation proportional to the question.
- Oracle, [Java Virtual Machine Technology Overview, §1 (Java SE 21 documentation)](https://docs.oracle.com/en/java/javase/21/vm/java-virtual-machine-technology-overview.html). Inspected adaptive compilation of hot code, allocation/garbage collection, and synchronization. This Oracle-hosted Java documentation supports the applicability limit of older native-code assumptions and motivates distinguishing warm-up, allocation, and concurrency only when the target workload exhibits them; it is specific to HotSpot/JVM and does not prescribe universal warm-up settings.
- OpenJDK, [JMH README and benchmark guidance](https://github.com/openjdk/jmh/blob/master/README.md). Inspected guidance on standalone benchmark setup, uncontrolled IDE environments, generated harness code, and sample/peer review. This is tool guidance, not a book or a guarantee that a harness makes a benchmark valid. Apply the broader lesson—harness choice cannot replace sound workload and measurement design—without requiring JMH.
- Linux kernel documentation, [Control Group v2](https://docs.kernel.org/admin-guide/cgroup-v2.html), sections `cpu.max`, `cpu.stat`, `memory.high`, and `memory.max`. Inspected CPU bandwidth limits and memory throttling/limits. This grounds container/cgroup resource ceilings as possible workload conditions on Linux; it is platform-specific and does not imply every container uses cgroup v2 or has a quota.
- Victor Stinner et al., [pyperf: Run a benchmark](https://pyperf.readthedocs.io/en/latest/run_benchmark.html). Inspected calibrated loops, multiple worker processes and values, warmups, instability warnings, system jitter, and runtime/JIT warm-up. Its configuration and Python-specific options apply to pyperf; this skill generalizes attention to runtime state and variability without requiring pyperf or a fixed repetition count.
- Brendan Gregg, [USE Method: Linux Performance Checklist](https://www.brendangregg.com/USEmethod/use-linux.html). Inspected Linux-specific organization of resource evidence around utilization, saturation, and errors across CPU, memory, network, and storage. This supports looking for a limiting resource rather than assuming CPU; commands and metrics are Linux-specific and optional.
- Linux kernel documentation, [Page Cache](https://docs.kernel.org/mm/page_cache.html), and [CPU Performance Scaling](https://docs.kernel.org/admin-guide/pm/cpufreq.html). Inspected normal filesystem page-cache use and dynamic CPU frequency/capacity tradeoffs. These ground warm/cold I/O and changing CPU conditions as possible sources of unlike measurements on Linux; neither prescribes manual cache flushing or frequency locking.

The central guidance is an original synthesis: define a workload and objective, find the limiting cost, make a correctness-preserving change, and stop when evidence no longer supports added complexity. Examples in [Measurement and Tradeoffs](measurement-and-tradeoffs.md) illustrate reasoning, not source-reported effect sizes. Book principles are qualified where their era or service-operations context limits transfer; modern runtime and platform details come from the primary documentation listed above. No profiler, benchmark framework, statistical test, warm-up count, percentage gain, coding idiom, or hardware setting is mandatory. Reliability-principles remains the focused guide for overload, timeouts, retries, partial failures, and recovery; performance guidance may identify resource pressure but does not replace that work when failure handling is the concern.
