# Measurement and Tradeoffs

Use this reference when a performance result is disputed, a benchmark is being designed, or a specific resource tradeoff needs closer analysis. The examples are illustrative, not universal thresholds.

## A defensible comparison

1. **Fix the question first.** State the operation, representative input and distribution, target metric, environment, and decision threshold. Examples: p95 end-to-end latency for 1 KiB reads at 40 concurrent clients; records/second for a batch of one million realistic records; peak resident memory while processing a 2 GiB input. For managed runtimes, say whether startup or warmed behavior is in scope; for parallel workloads, state concurrency. Include deployment limits when relevant, such as a container CPU quota or memory limit. A target should come from the task or users, not merely from the fastest result currently observed.
2. **Make both candidates do the same useful work.** Check output, error behavior, and completion. Include parsing, setup, allocation, serialization, and I/O if users pay those costs. Exclude setup only when the actual use repeatedly amortizes it, and state that choice.
3. **Control major conditions.** Keep compiler/runtime/build flags, machine or deployment class, input, concurrency, and measurement boundaries comparable. Note background load, power/thermal variation, frequency scaling, cache state, JIT or lazy initialization, garbage collection, and storage/network state when they can affect the result. For containers, record relevant CPU/memory limits rather than inferring available capacity from host core count. Alternate or randomize candidate order when drift is plausible. Use enough independent repetitions to see variation; rerun or extend measurements when the difference is comparable to noise.
4. **Use the right view of the data.** For interactive latency, report a distribution or relevant quantiles (often median and a tail percentile), define the measurement boundary and sample window, and ensure the sample can meaningfully represent the tail being discussed. A mean alone can conceal slow requests. For throughput, report completed useful work per unit time at a stated concurrency and input mix; pair it with latency and resource use where saturation or queueing is possible. For finite jobs, report end-to-end elapsed time and relevant peak resources. Do not compare unlike windows, denominators, or units.
5. **Measure cause separately from outcome.** A sampled profile or counter can reveal where time or resources go, but collection overhead and attribution can distort short operations. First profile to form a bottleneck hypothesis; then make a controlled change and verify the user-relevant metric without the profiler. If end-to-end time is dominated by network or storage latency, a CPU-only microbenchmark may answer the wrong question.
6. **Keep evidence and limits together.** Record versions, configuration, workload generation, warm-up policy, repetitions, raw or summarized results, and known environmental differences. Report direction and magnitude plus uncertainty; avoid a precise percentage when the measurements do not support it.

### Misleading benchmark patterns

- **One short run:** Candidate A takes 10.0 ms and B takes 9.8 ms once. Scheduler noise, background work, or clock changes could exceed 0.2 ms. This is not evidence of a 2% improvement; repeat under controlled conditions and inspect spread.
- **Unrepresentative microbenchmark:** A tight loop over an already-resident tiny array improves 30%, but production reads a large, irregular dataset from storage. The result measures a different workload and cannot justify an end-to-end claim.
- **Work removed rather than accelerated:** A new parser benchmark skips validation or returns a partial result. Compare equivalent outputs and failure behavior before timing.
- **Warm-only cache:** Repeatedly reading the same key measures cache hits, while deployment mostly sees cold or changing keys. Report warm and cold cases if both occur; do not silently substitute one for the other.
- **Throughput hides delay:** Batches raise throughput from 8,000 to 12,000 items/s, but p95 per-item response rises from 40 to 180 ms and buffering increases. Whether this is better depends on separate throughput, latency, and memory objectives.
- **Profiler becomes the workload:** Instrumentation makes a short allocation-heavy function appear disproportionately expensive, or tracing every event changes contention. Use the trace to locate candidates, then confirm with lower-overhead outcome measurements.
- **Single average hides tails:** Most requests take 20 ms, but 1 in 100 takes 900 ms. An average can look acceptable while a latency-sensitive caller experiences slow requests. Report distribution and population, not an unqualified “average latency.”

## Scaling and resource tradeoffs

- **Algorithmic growth:** Test representative sizes, not just one point. If work grows quadratically, doubling input can produce roughly four times the dominant work in the relevant range; treat this as a hypothesis to check, since setup cost and cache boundaries can produce several regimes. A lower asymptotic cost often matters at scale, but small inputs may favor the simpler implementation. State the supported size range.
- **Allocation and memory:** Count bytes/allocations per operation, peak live/resident memory, collection or paging effects, and copies where relevant. In a garbage-collected runtime, allocation rate and retained live data can affect different costs; inspect runtime evidence rather than assuming fewer allocations or a forced collection is always beneficial. Pooling can reduce allocation churn while increasing retained footprint and ownership complexity; check whether a container limit changes the consequences. Keep such changes only if the target workload benefits and lifetime rules remain clear.
- **Locality and cache:** Compact or sequential access may improve locality, but extra tables and duplicated representations consume memory and need coherent updates. A cache's useful benefit depends on hit rate, miss cost, freshness requirements, and invalidation path. A cached benchmark with no invalidation or cold-start cost is incomplete when those costs exist in use.
- **I/O:** Separate fixed per-operation latency from transfer cost. Combining small operations can amortize round trips or startup costs, but larger batches may delay the first result and consume more memory. Compression trades CPU and memory for fewer bytes; decide using the constrained resource and representative payloads. Measure actual I/O and end-to-end behavior rather than assuming bandwidth or CPU is dominant.
- **Resource ceilings:** Include deployment limits such as memory budgets, file descriptors, worker/concurrency limits, CPU quotas, and storage/network caps. Host capacity is not necessarily the capacity available to a process: on Linux cgroup v2, for example, `cpu.max` can cap CPU bandwidth and `memory.high`/`memory.max` can throttle or limit memory. Other runtimes and platforms expose different controls. An improvement that exceeds an actual peak-memory limit, increases queue growth, or is throttled by its resource ceiling is not useful even if its local elapsed time improves.

## Evidence and stopping

A useful change record can be concise:

> Workload: 1 KiB lookups, 40 concurrent clients, warmed and cold cases, deployed with a 2-CPU quota and 256 MiB memory limit. Objective: p95 under 80 ms; stay within the memory limit. Baseline and candidate use the same runtime/build and input mix; both return equivalent results. Candidate p95 is 72 ms warmed and 109 ms cold, with 214 MiB peak memory. Paired runs on the same deployment show a spread of 4–7 ms. Improvement meets the warmed target but not the cold target; memory is within the limit. Further work should target cold I/O, not another CPU micro-optimization. For a JIT runtime, include startup in the objective only if users pay startup cost; do not mix cold-start and warmed samples into an unexplained average.

Do not treat those values as prescribed thresholds. Stop once the stated objectives are met with adequate margin, or when repeated measurements cannot distinguish a useful gain from noise, or the remaining gain costs more in complexity, memory, power, correctness risk, or operational burden than it is worth. If evidence is insufficient, say so and keep the simpler implementation unless the performance requirement itself demands a decision.
