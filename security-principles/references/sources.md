# Sources and evidence boundaries

This reference records inspected chapter prose and current primary standards material. Author advice, standard scope, and synthesis are identified separately. The sources are not controlled evidence that a skill or slogan improves outcomes.

## Inspected chapters

- Loren Kohnfelder, *Designing Secure Software: A Guide for Developers* (No Starch Press, 2021), Chapter 4, “Patterns.” The full publisher-hosted sample PDF was inspected. It discusses economy/transparent design, least privilege and least information, secure defaults, allowlists, fail securely, complete mediation, least common mechanism, defense in depth, separation of privilege, reluctance to trust, and responsibility. It cautions against mechanical application when complexity and overhead exceed marginal protection. Chapter 4 only—not the whole book. [Publisher sample PDF](https://nostarch.com/download/DesigningSecureSoftware_Ch4.pdf).
- Tanya Janca, *Alice and Bob Learn Secure Coding* (Wiley, 2025), Chapter 1, “Introductory Security Fundamentals.” Inspected the actual Wiley-authorized chapter excerpt, including implied trust, least privilege, secure defaults, assume breach, defense in depth, supply-chain concerns, usable security, fail closed/safe, rollback, and threat modeling. These are author recommendations; the chapter's rollback/retry guidance is not a universal guarantee that effects can be reversed. Chapter 1 excerpt only. [Wiley chapter excerpt PDF](https://media.wiley.com/product_data/excerpt/06/13941717/1394171706-5.pdf); [publisher page](https://www.wiley.com/en-us/alice-and-bob-learn-secure-coding-p-9781394171712).
- Ross Anderson, *Security Engineering*, 3rd ed. (2020), author-hosted Chapters 1 (“What Is Security Engineering?”), 3 (“Psychology and Usability”), 6 (“Access Control”), and 27 (“Secure Systems Development”). Inspected Chapter 1 §§1.1–1.2; Chapter 3 §§3.2.1 and 3.2.5.3; Chapter 6 §§6.1–6.2; Chapter 27 §§27.2–27.5.1. They cover system boundaries, policy/mechanism/assurance, human factors/defaults, principals and access-control tradeoffs, risk/threat analysis, and safe-state counterexamples. Four chapters only; technology examples may be dated. [Author's chapter index](https://www.cl.cam.ac.uk/archive/rja14/book.html); [Chapter 6](https://www.cl.cam.ac.uk/archive/rja14/Papers/SEv3-ch06.pdf); [Chapter 27](https://www.cl.cam.ac.uk/archive/rja14/Papers/SEv3-ch27.pdf).

## Current standards and scope

- OWASP Application Security Verification Standard (ASVS) **5.0.0**, released 2025-05-30 per official project material, is a framework of testable requirements for web applications and web services. The official versioned downloads include requirements for validation, authorization, path consistency, SSRF controls, and transactional business logic (for example, v5.0.0 V2.3.3). Requirement identifiers are version-specific. Apply only relevant controls; ASVS is not a universal software-quality or security rubric for every domain. [Overview](https://asvs.owasp.org/); [versioned downloads](https://asvs.owasp.org/downloads/).
- NIST SP 800-218, Secure Software Development Framework (SSDF) **v1.1**, is final lifecycle/process guidance intended to integrate into different SDLC models. The official NIST publication/status page lists SSDF v1.1 as final and SP 800-218 Rev. 1 / SSDF v1.2 as draft dated December 17, 2025; check that status before use. SSDF structures producer practices; it is not an application-level control catalog. As of 2026-11-21, refer to v1.1 as the final baseline and explicitly call v1.2 draft. [NIST publications/status table](https://csrc.nist.gov/projects/ssdf/publications); [final v1.1 publication](https://csrc.nist.gov/pubs/sp/800/218/final).

## Synthesis and boundaries

Threat framing as assets, attackers, principals, resources, and trust boundaries synthesizes Anderson's system/policy/threat analysis with the chapter advice on implied trust and access control. Applying policy at every path to a protected operation follows complete mediation; favoring a shared trusted guard versus independent layers is a design synthesis, not a call to duplicate checks. Least privilege should be scoped to enforceable boundaries because over-granularity and unusable policy can drive errors and workarounds.

“Fail closed” is qualified: deny the protected action when authorization is invalid or unavailable, but choose service/safety behavior per hazard. This reconciles Janca's chapter 1 “fail closed/safe, then roll back” advice with Anderson's safe-state counterexample and Kohnfelder's fail-securely pattern. A database transaction may roll back uncommitted state; a committed external effect may not be reversible. A timeout does not prove non-commit, and automatic retry is safe only under an actual idempotency or status-resolution contract. Do not universalize Janca's rollback/retry language.

ASVS and SSDF corroborate selected practice only within their scope; neither proves every book-level principle or dictates identical controls across domains. Dependence review and secret protection should follow changed trust boundaries and existing lifecycle controls, not become blanket duplicated audits.

## Decision examples: why and how to check

1. **A user can request an object by identifier.** Why: authentication alone does not establish authority over that resource. How to check: test ownership/tenant policy at the server-side trusted boundary and through alternate access paths; do not rely on a hidden UI control. Use relevant ASVS v5.0.0 controls if this is a web application/service.
2. **A machine-control authorization dependency fails.** Why: granting operation on uncertainty violates access policy, while stopping all operations may create a physical hazard. How to check: deny the protected command, analyze the domain safe state, and test any bounded emergency mode for authority, audit, and independent safeguards. Neither “always fail open” nor “always shut down everything” follows.
3. **A payment succeeds remotely but the response is lost.** Why: rollback of local work cannot undo a committed external charge; blind retry may charge twice. How to check: use provider-defined durable idempotency/status reconciliation, test timeout-after-commit and key reuse, and state the retention/scope. If unsupported, reconcile or forward-repair rather than claiming rollback.
