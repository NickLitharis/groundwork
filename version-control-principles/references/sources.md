# Sources, claims, and limits

This map distinguishes (1) principles grounded in the inspected portions of a real book, (2) current Git or host-specific mechanics, and (3) this skill’s own synthesis. Git documentation explains command behavior; it does not prescribe one workflow for every team. The core remains conditional on repository instructions and collaboration context.

## Book foundation: inspected sections

Scott Chacon and Ben Straub, *Pro Git*, 2nd ed. (Apress, 2014), full text hosted by the Git project at [git-scm.com/book/en/v2](https://git-scm.com/book/en/v2/). The following substantive sections were inspected; this is not a claim to have read the whole book:

- **2.2, “Recording Changes to the Repository”** — the working-tree file lifecycle, tracked/untracked states, `status`, adding and staging, staged content as a snapshot at the time of `add`, edits after staging, and viewing staged vs unstaged diffs. Supports the distinction between committed `HEAD`, proposed index, and working tree, and the advice to review and update only the intended staged content. [Section](https://git-scm.com/book/en/v2/Git-Basics-Recording-Changes-to-the-Repository)
- **2.4, “Undoing Things”** — amending replaces the previous commit; only amend unpublished commits; unstaging differs from discarding working-tree edits; reset and checkout examples can lose work; committed data is usually recoverable while never-committed data may not be. Supports cautious separation of recovery operations and limits on promises to restore lost work. [Section](https://git-scm.com/book/en/v2/Git-Basics-Undoing-Things)
- **3.2, “Basic Branching and Merging”** — branch pointers, switching worktree state, fast-forward and three-way merges, divergence, and merge conflict resolution. Supports describing branches as alternative histories and checking the integrated result rather than treating a merge as mere file selection. [Section](https://git-scm.com/book/en/v2/Git-Branching-Basic-Branching-and-Merging)
- **3.4, “Branching Workflows”** — topic branches and long-running branches as alternatives, explicitly noting long-running branches are not necessary for every project. Supports a conditional choice of branch strategy, not a mandatory model. [Section](https://git-scm.com/book/en/v2/Git-Branching-Branching-Workflows)
- **3.6, “Rebasing”** — replaying commits onto a new base, resulting history shape, and the risks when published commits are rewritten. Supports the merge/rebase distinction and collaboration caution. [Section](https://git-scm.com/book/en/v2/Git-Branching-Rebasing)
- **5.1, “Distributed Workflows”** — centralized, integration-manager, and dictator/lieutenant collaboration patterns, with tradeoffs and combinations. Supports adapting the process to project structure rather than imposing a single workflow. [Section](https://git-scm.com/book/en/v2/Distributed-Git-Distributed-Workflows)
- **5.2, “Contributing to a Project”** — contribution practices vary with contributor count, access, review, and integration process; coherent changes and messages ease review and selective rollback; pushes can be rejected when the remote advanced. Supports checking project contribution guidance, keeping useful changesets, and integrating others’ commits rather than bypassing them. Its sample commit-message details are not imposed where repository policy differs. [Section](https://git-scm.com/book/en/v2/Distributed-Git-Contributing-to-a-Project)
- **7.6, “Rewriting History”** — amend and interactive rebase can change commit identities, contents, order, and membership; examples concern shaping local history before sharing and warn against rewriting already-pushed commits. Supports treating rewrite as a coordination boundary, not routine cleanup of shared history. [Section](https://git-scm.com/book/en/v2/Git-Tools-Rewriting-History)
- **7.7, “Reset Demystified”** — HEAD, index, and working tree effects vary by reset mode. Supports warning that reset is not interchangeable with revert or unstage. [Section](https://git-scm.com/book/en/v2/Git-Tools-Reset-Demystified)
- **10.7, “Maintenance and Data Recovery”** — reflogs record local reference movement; examples recover abandoned commits by finding a prior tip; unreachable objects may be found with lower-level recovery tools. Supports a qualified reflog recovery suggestion, not guaranteed recovery. The section does not claim recovery of arbitrary unstaged or untracked file contents. [Section](https://git-scm.com/book/en/v2/Git-Internals-Maintenance-and-Data-Recovery)

## Current primary documentation and official policy

The current Git project manuals were inspected at the latest-version documentation pages linked here:

- [`git status`](https://git-scm.com/docs/git-status) — differences between index-vs-HEAD, worktree-vs-index, and visible untracked paths; verbose status can show staged/unstaged patch content. It cannot reveal edits not visible to Git or guarantee the workspace stays unchanged after inspection.
- [`git add`](https://git-scm.com/docs/git-add) — adds selected contents to the index; `-p` allows hunk selection; repeated adds update staged contents; directory pathspecs can include additions and deletions. Grounds scoped staging mechanics, not the user’s intended scope.
- [`git commit`](https://git-scm.com/docs/git-commit) — ordinary commit records index contents, with path/patch/`-a` alternatives behaving differently. Supports checking exactly what the chosen commit mechanism will record.
- [`git merge`](https://git-scm.com/docs/git-merge) — joins histories, stops for unresolved conflicts, and has abort/continue operations; abort may not restore the original uncommitted changes if the worktree was dirty. Supports avoiding risky integration atop valuable uncommitted work.
- [`git rebase`](https://git-scm.com/docs/git-rebase) — reapplies commits, can edit/reorder/combine them, and stops on conflicts. Supports mechanics only; coordination requirements are collaboration safety.
- [`git push`](https://git-scm.com/docs/git-push) — updates remote refs and rejects non-fast-forward updates by default; force options can override. Supports treating a rejected push as an integration signal, not as permission to overwrite.
- [`git revert`](https://git-scm.com/docs/git-revert) and [`git restore`](https://git-scm.com/docs/git-restore) — revert records new commits counteracting existing patches; restore changes selected index and/or working-tree contents. Supports distinguishing them from reset and checking effects before use.
- [`git reset`](https://git-scm.com/docs/git-reset) — moves HEAD and can update the index and worktree according to mode; `--hard` replaces tracked content and may overwrite untracked files. Supports the caution that effects are mode-dependent.
- [`git reflog`](https://git-scm.com/docs/git-reflog) — records local reference-tip movements and prunes entries according to expiration policy. Supports its limited, local, time-bounded role in recovery, not a backup guarantee.
- [`git blame`](https://git-scm.com/docs/git-blame) — annotates lines with the revision that last modified them and can follow moved/copied lines; deleted/replaced lines require other history searches. Supports treating attribution as an investigative clue, not proof of cause.
- [`git bisect`](https://git-scm.com/docs/git-bisect) — binary-searches a supplied property between caller-identified good/bad revisions. Supports the limit that the result depends on reproducible tests and those assumptions.
- [`gitignore`](https://git-scm.com/docs/gitignore) — patterns specify intentionally untracked files and do not affect already tracked files. Supports checking tracked status separately from ignore rules.

For a host-specific example of modern collaboration constraints, GitHub’s official [protected branches documentation](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) documents configurable review, status-check, signing, merge-queue, force-push, and deletion rules. These settings are optional and host-specific; check the project’s actual rules rather than assuming every feature or policy is in use.

## Modern adaptation and original synthesis

**Book-derived:** staged content is a proposed snapshot; commits should be intelligible; branch and distributed workflows have alternatives; rewriting published history affects collaborators; recovery is not equally reliable for committed and uncommitted work.

**Dated or conditional:** Pro Git’s examples use GitHub-era terminology and specific branch names, commit-message conventions, and workflows. They are illustrations, not universal policy. Current default branch names, host protections, review/CI queues, signing requirements, and prescribed contribution tools vary by repository and change over time.

**Modern adaptation:** consult repository instructions, automation, and protections before choosing a tool or integration path; use the designated commit/PR workflow before generic command sequences; account for concurrent editors/agents sharing one worktree and index by coordinating and refreshing diffs; treat a rejected push as a cue to integrate under policy; and verify semantic behavior after resolving a conflict. Current Git manuals ground command details; host docs ground optional platform features.

**Original synthesis:** prefer the least disruptive action that preserves all known work; do not clean or overwrite another owner’s edits, discard user work, force-push, or rewrite shared history without explicit authorization and coordination. Review staged content, integrated behavior, callers, and relevant tests—not only textual conflict status or compile success. These are conservative collaboration principles inferred from the mechanics and risks above, not claims that the book or Git enforce them.

**Limits:** Git status and the index do not provide a transaction across collaborators or concurrent processes. A reflog may expire and cannot restore arbitrary uncommitted file contents. A syntactically clean merge or passing tests may still miss a domain invariant. No branch model, host policy, test suite, or recovery outcome is universally appropriate.
