# Sources and evidence boundaries

This reference maps the skill's recommendations to material actually inspected. PostgreSQL documentation below is implementation documentation for PostgreSQL 19 (current as inspected on 2026-11-21), not a universal data-modeling standard. JSON Schema documentation describes that format's documented rules. The identity, ownership, representation-selection, and example practices are conditional synthesis for this skill—not quotations, scientific laws, or claims of measured effectiveness.

## Book foundation

### Adrienne Watt and Nelson Eng, *Database Design*, 2nd edition

Published by BCcampus Open Education (2014), CC BY 4.0 except where otherwise noted. I inspected substantive full-text passages—not only the contents pages—in:

- **Chapter 7, “The Relational Data Model”**: relations/rows/attributes, domains as sets of acceptable values, and the idea that a value is atomic relative to a model. This grounds checking that a field's permitted values and decomposition fit the chosen representation; “atomic” is relational-model terminology, not a ban on structured JSON or nested values in every system. [Chapter 7](https://opentextbc.ca/dbdesign01/chapter/chapter-7-the-relational-data-model/)
- **Chapter 9, “Integrity Rules and Constraints”**: domain, entity, and referential integrity; user-supplied business rules; and relationship cardinality/optionality. This supports translating domain rules into explicit invariants and checking where a relational engine can enforce them. Its examples use relational tables and some older Access/SQL Server idioms; the meaning of a rule must be established independently of those mechanisms. [Chapter 9](https://opentextbc.ca/dbdesign01/chapter/chapter-9-integrity-rules-and-constraints/)
- **Chapter 11, “Functional Dependencies”**: determinants and dependents, dependencies involving composite keys, partial and transitive dependencies, and discussion of joining or separating attributes. This grounds asking which facts determine others and whether repeated values can be independently changed. [Chapter 11](https://opentextbc.ca/dbdesign01/chapter/chapter-11-functional-dependencies/)
- **Chapter 12, “Normalization”**: normalization as relational analysis of redundancy; 1NF–BCNF concepts and examples; and insertion, update, and deletion anomalies. It presents normalization alongside ER modeling and shows why assumptions about business rules and keys affect decomposition. This supports using dependency/anomaly analysis as a diagnostic, not a universal prescription to normalize non-relational models or optimize for a normal form regardless of consumers. [Chapter 12](https://opentextbc.ca/dbdesign01/chapter/chapter-12-normalization/)

The book is a genuine, readable design textbook and was read directly for this revision. Its scope is relational database design; it does not substantiate modern API omission rules, JSON/event semantics, time-zone behavior, or a universal storage strategy. Those claims are grounded below in current format/platform documentation or explicitly marked as synthesis. No exact page numbers are supplied because the web text was read in chapter form and pagination may differ by edition/format.

## Inspected primary sources


- **PostgreSQL 19, Numeric Types, §8.1.** The inspected text says `numeric`/`decimal` are exact and recommends them for monetary amounts or other quantities requiring exactness; floating-point types are inexact and may produce approximation discrepancies. It documents scale coercion/rounding, precision limits, and different tie rounding behavior. This supports checking precision, range, rounding, and actual platform semantics. It does not imply that floating point is always wrong or that PostgreSQL's rules transfer to another database/runtime. [Documentation](https://www.postgresql.org/docs/current/datatype-numeric.html)
- **PostgreSQL 19, Monetary Types, §8.2.** The inspected text says `money` fractional precision depends on `lc_monetary`, output depends on locale, and floating-point conversion is not recommended due to potential rounding errors. This supports explicitly checking currency and locale-sensitive behavior, not a blanket prohibition on any specific representation. [Documentation](https://www.postgresql.org/docs/current/datatype-money.html)
- **PostgreSQL 19, Date/Time Types, §8.5.** The inspected text distinguishes date/time types and says `timestamp with time zone` inputs are converted to UTC; the original zone is not retained. It also describes time-zone rules as subject to political change and distinguishes full zone names from offset abbreviations. This supports naming temporal meaning and checking whether the original civil zone must be retained. These are PostgreSQL semantics, not a general schema prescription. [Documentation](https://www.postgresql.org/docs/current/datatype-datetime.html)
- **PostgreSQL 19, Comparison Functions and Operators, §9.2.** The inspected text states that ordinary comparison with `NULL` yields null/unknown and documents `IS [NOT] DISTINCT FROM` as null-aware equality predicates. This supports checking null semantics where SQL is used; it does not assign a business meaning to null. [Documentation](https://www.postgresql.org/docs/current/functions-comparison.html)
- **PostgreSQL 19, Constraints, §5.5.** The inspected text describes check, not-null, unique, and primary-key constraints, including the requirement that primary keys be unique and non-null and default handling of nulls in unique constraints. It supports checking where invariants can be enforced and the specific engine's behavior; constraints alone do not discover the domain rule. [Documentation](https://www.postgresql.org/docs/current/ddl-constraints.html)
- **PostgreSQL 19, JSON Types, §8.14.** The inspected text distinguishes `json` (preserves input text) from `jsonb` (decomposed representation with indexing and different key/whitespace behavior), describes JSON/SQL null differences, and advises predictable document structure. Its design and indexing sections give examples of query-specific indexes and atomic document boundaries. This supports treating document and relational representations as options with concrete trade-offs, not asserting that one dominates. [Documentation](https://www.postgresql.org/docs/current/datatype-json.html)
- **JSON Schema, Understanding JSON Schema: “object.”** The inspected documentation says object properties are optional by default, additional properties are allowed by default, and `required` can express required property names. This supports explicit boundary rules for omission and unknown properties. It is documentation for JSON Schema's object validation, not a claim about every API schema or JSON parser. [Documentation](https://json-schema.org/understanding-json-schema/reference/object)
- **CloudEvents specification, current `main` draft inspected (version 1.0.3-wip), “Overview,” event definitions, and context attributes (`id`, `source`, `type`, `time`).** It defines an event as a record expressing an occurrence and its context; `source` + `id` identifies a distinct event, while `type` describes the kind of occurrence. Its `time` denotes when the occurrence happened, with a documented fallback when that time cannot be determined. The spec separates event data from context metadata and allows different encodings/bindings. This grounds explicit event meaning and identity, but does **not** promise a complete history, replayability, event sourcing, or that an event is the source of truth. Because this URL tracks a work-in-progress draft, inspect the version actually adopted by a system before relying on its details. [Specification](https://github.com/cloudevents/spec/blob/main/cloudevents/spec.md)

## Book-derived principles and modern synthesis

The book directly supports making domains, integrity rules, relationship cardinality, dependencies, and redundancy/anomalies explicit **within relational modeling**. Adapting those checks across records, API payloads, JSON documents, events, and projections is the skill author's synthesis, checked against the format/platform references above. Identity lifetime, units, monetary and temporal semantics, null/absence, authority per fact, and consumer-driven representation choice are conditional modeling recommendations; they are not claims that BCcampus teaches those topics in the listed chapters.

The detailed worked examples in [modeling-examples.md](modeling-examples.md) are authored scenarios, not cases quoted from the book or implementation documentation. Check the actual database, language, interchange schema, or event specification in use; the cited PostgreSQL rules are product-specific, JSON Schema rules are format-specific, and the CloudEvents URL is a work-in-progress draft.

## Limits

This source review does not establish a universally best identity strategy, normalization level, schema shape, or temporal/money representation. The operational recommendations are reasoned synthesis, not empirical findings, author quotations, or guarantees that any skill improves outcomes. The inspected implementation documentation is PostgreSQL-specific; check the actual storage, language, and interchange layers in use. For an existing persisted/API/event contract, transition and rollout practices belong to [evolution-principles](../../evolution-principles/SKILL.md); for races, partial failure, and recovery, use [reliability-principles](../../reliability-principles/SKILL.md).
