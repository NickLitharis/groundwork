# Chapter foundations and decision examples

This reference records the inspected material behind the core guidance. It is a source map, not a claim that any source proves this skill effective. The original sources are further reading only; applying the skill does not require network access.

## Inspected sources and boundaries

- **John Ousterhout, *A Philosophy of Software Design*, 2nd ed.** The author-hosted [official extract PDF](https://web.stanford.edu/~ouster/cgi-bin/aposd2ndEdExtract.pdf) was read from rendered page images. Inspected: Chapter 6, “General-Purpose Modules are Deeper,” §§6.1–6.9 (book pp. 39–49); Chapter 21, “Decide What Matters,” §§21.1–21.4 (pp. 171–174); and the comparisons on method length (p. 76) and comments (pp. 99–100). Chapter 6 supports interfaces that are somewhat general-purpose for known uses while warning against speculative generality. Chapter 21 offers leverage and visibility as judgment heuristics, not a scoring method. His method-length and comment positions are one side of a documented style disagreement, not settled law.
- **Eric S. Raymond, *The Art of Unix Programming* (2003).** Inspected full-text [PDF](https://cdn.nakamotoinstitute.org/docs/taoup.pdf): Chapter 11, “Interfaces,” especially “Evaluating Interface Designs,” “Tradeoffs between CLI and Visual Interfaces,” “The Filter Pattern,” and “The Separated Engine and Interface Pattern”; Chapter 12, “Optimization,” especially “Measure before Optimizing” and “Throughput vs. Latency”; Chapter 13, “Complexity,” especially “The Three Sources of Complexity,” “Essential, Optional, and Accidental Complexity,” and “The Right Size of Software.” These are Raymond’s design arguments and examples, including period-bound examples; the core applies them as conditional reasoning, not universal interface or size rules. See [Complexity, Interfaces, and Performance](complexity-performance.md) for expanded application.
- **Titus Winters, Tom Manshreck, and Hyrum Wright, *Software Engineering at Google* (2020).** Read actual public text: [Chapter 8](https://abseil.io/resources/swe-book/html/ch08.html) “Why Have Rules?,” “Guiding Principles,” “Concede to practicalities,” and “Changing the Rules”; [Chapter 9](https://abseil.io/resources/swe-book/html/ch09.html) “Code Review Benefits” and “Write Small Changes”; [Chapter 11](https://abseil.io/resources/swe-book/html/ch11.html) “Designing a Test Suite,” “Test Scope,” and “A Note on Code Coverage”; [Chapter 12](https://abseil.io/resources/swe-book/html/ch12.html) “Strive for Unchanging Tests,” “Test via Public APIs,” and “Test State, Not Interactions.” These are practitioner guidance from Google’s unusually large monorepo, not default ratios, review-size limits, or universal testing laws. Green tests only support what their assertions and exercised scope establish; coverage measures execution, not assertion quality.
- **David Farley, *Modern Software Engineering* (2021).** Inspected the Pearson [official sample](https://ptgmedia.pearsoncmg.com/images/9780137314911/samplepages/9780137314911_Sample.pdf), specifically the preface and Chapter 3, “Fundamentals of an Engineering Approach,” including “The Importance of Measurement.” The sample table of contents lists design chapter topics but their prose was unavailable; no detailed claims about chapters 9–13 are attributed here. Farley’s inspected text advocates empirical problem-solving and meaningful outcome measures; it says productivity itself is not directly measurable and describes reported delivery associations as correlations, not proof of causation.

## Synthesis boundaries

The recommendations below combine the inspected authors’ advice with practical synthesis for code changes. They do not imply that the authors all agree, that a technique is empirically optimal, or that this skill has been evaluated. Keep established security, compatibility, performance, and Unix guidance in the core; use the focused companion skills for deeper diagnosis, testing, evolution, reliability, or security work rather than duplicating their manuals.

## Decision examples: why and how to check

1. **Shared mechanism or caller-specific interface?** Two consumers need text insertion, but only one has a “delete selection” UI action. Keep a mechanism-level insert/delete/position interface if both callers can use it; implement selection policy at the UI boundary. This is somewhat general for identifiable consumers, not a plugin framework for guessed futures. Check whether the shared contract expresses domain operations, whether each caller can use it without leaking its policy, and whether tests cover both relevant call paths.
2. **Split a long function or keep it cohesive?** A 45-line transaction coordinates state changes and rollback; extracting each few-line block would add interfaces and hide the invariant. Keep the cohesive operation or extract only a meaningful boundary, and comment the non-obvious invariant. Judge the whole reading and change cost, not a line threshold. Check that the invariant remains visible, that error paths are understandable, and that any extraction has a useful contract.
3. **Are green tests enough to claim a refactor is safe?** A unit test passes after changing a serializer, but does not exercise persisted output consumed by another version. Treat the pass as evidence only for its asserted behavior; inspect compatibility needs and add an appropriate consumer or format-level check if the boundary matters. Check what ran, what each assertion observes, and which externally relied-on behavior remains untested.
